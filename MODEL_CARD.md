#### Description

`imageomics/bioclip-2` is the Imageomics Institute's BioCLIP 2 (Gu, Stevens, Campolongo et al., NeurIPS 2025; arXiv:2505.23883), pinned here to revision `2957b322090f9cb17ae72c71981c7218a28d81e0`. It is a CLIP model — a ViT-L/14 image tower (24 layers, width 1,024, patch 14, 224×224 input) and a 12-layer masked-attention text tower (width 768, 77-token context, 49,408-token vocabulary) projecting into a shared 768-dimensional space — initialised from the LAION-2B ViT-L/14 CLIP and trained with hierarchical contrastive learning on TreeOfLife-200M, which the upstream card describes as nearly 214 million images covering 952 thousand taxa, with a 26-million-sample LAION-2B subset for experience replay. The pinned `open_clip_model.safetensors` holds 427,616,513 parameters, 303,966,208 of them in the image tower. Because images and taxon names share one space, the model classifies a photograph against any list of names with no training (zero-shot), and the upstream paper reports that this training also yields representations that separate traits and ecological attributes beyond species.

What this repository adds is the `BioClip2Pipeline` class in `src/bioclip2_biodiversity_pipeline/pipeline.py`: manifest verification of the 3-file snapshot before any model library is imported (`verify_snapshot`), fresh-clone staging at the pinned revision only (`stage_missing_files`), a loader that **builds `open_clip.model.CLIP` from the pinned `open_clip_config.json`** rather than from open_clip's built-in registry and loads the safetensors state dict with `strict=True` — no remote code, no fallback download — image validation by decoding with named ceilings (`decode_image`, `validate_inputs`), L2-normalised image and text embeddings (`embed_images`, `embed_texts`), zero-shot classification from a label set with BioCLIP's `a photo of <name>.` prompt convention (`zero_shot`, `zero_shot_evaluate`), bounded gradient fine-tuning of a linear head over the frozen image tower's projection — **initialised from the zero-shot text classifier**, so training starts where zero-shot stands and every epoch is comparable to it (`adapt`) — held-out metrics (`evaluate`), argmax classification with per-class scores (`classify`), and a safetensors adapter artifact that is digest-verified before deserialization (`save_artifact`, `from_artifact`).

Two design choices are stated rather than hidden. The **text tokenizer is open_clip's bundled CLIP BPE**, not the `tokenizer.json` the upstream repository also ships: both encode the same 49,408-token CLIP vocabulary, identical token ids were verified for the tutorial prompts, and the HF tokenizer files are therefore not staged (`docs/WEIGHTS.md`). And **head-only adaptation is the default** (`trainable_blocks=0`): on the tutorial sample, unfreezing even one of the 24 image-tower blocks took a saturated zero-shot classifier from 12/12 to 11/12 on the test split — 12.6 million parameters pulled around by 28 images — so the default trains 3,076 parameters on features the frozen tower computes once, and the degradation is recorded under "Runtime".

#### Intended Use and Limitations

###### Primary Intended Uses

Three tasks are exposed. **Zero-shot species classification:** input is 1 to `MAX_IMAGES_PER_CALL = 32` images (JPEG, PNG or WEBP bytes, paths or PIL images) and 2 to `MAX_LABELS = 64` labels — taxon names, or a `{label: taxon name}` mapping — with an optional prompt template; output is one label per image with a softmax score over the supplied label set. **Organism representation:** one L2-normalised 768-dimensional vector per image (and per text), suitable as features for a downstream model, for image-to-image or text-to-image similarity, or for clustering. **Species classification with local labels:** given a labelled dataset of `{id, image_bytes, label}` records with 2 to 50 classes, the pipeline fine-tunes a linear head (optionally with the last image-tower blocks) starting from the zero-shot classifier when scientific names are supplied, and then predicts a class with per-class scores. Envisioned application domains are biodiversity workflows where photographs of organisms exist — triaging citizen-science or camera-trap imagery against a candidate species list, building a first-pass classifier for a local site's taxa from a few dozen labelled photos, retrieving look-alikes across a collection, and teaching or evaluating vision-language transfer in biology. In a larger system the pipeline is a first-pass identifier and a feature extractor whose output feeds an expert's review, not an autonomous determination.

###### Primary Intended Users

Intended users are ecologists, taxonomists, conservation practitioners and machine-learning engineers working with organism imagery, in research, internal enterprise, or the DIMER model workbench. The pipeline assumes its users understand that zero-shot scores are relative to the label set they supplied and nothing else (a closed-set softmax always answers, even for a blank image — the tutorial shows it); that the pretraining corpus is long-tailed, so well-photographed taxa are recognised far better than rare, cryptic or poorly represented ones; that photographs of one individual, one photographer or one site leak across a random split; that the pipeline validates images by decoding them and nothing more, so a photo of a rock is embedded and classified without complaint; that the softmax scores are uncalibrated; and that location metadata, not classification capability, is the sensitive part of a biodiversity record.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline exposes closed-set zero-shot classification, embeddings and closed-set supervised classification only. It does not perform open-set or hierarchical (genus, family) prediction, detection or localisation of organisms within a frame, counting, image-to-image retrieval at scale, trait or attribute prediction as a task, or any of the published BioCLIP 2 benchmarks; it does not verify that a label names a real taxon, and it does not load the newer `imageomics/bioclip-2.5-vith14` checkpoint.
2. **Input boundary:** images must decode as JPEG, PNG or WEBP, have a shorter side of at least 32 px and a longer side of at most 8,192 px, and are resized so the shorter side is 224 px and centre-cropped — a small organism in a wide frame may be cropped out. At most 32 images per call and 64 labels per zero-shot call; a dataset needs at least 8 records, at least 3 per class, at most 5,000 records and at most 50 classes, with unique ids and unique image bytes. Video, multispectral rasters, specimen scans with rulers and labels, and non-image modalities are not inputs.
3. **Decision boundary:** not for autonomous action on a predicted species — regulatory or legal determinations, enforcement, culling or release decisions, medical or veterinary decisions, or any use where a wrong identification has consequences for an organism, a person or a protected population — without expert confirmation. A predicted species is a hypothesis for a specialist, not a determination.
4. **Ethical boundary:** not for locating or targeting protected, threatened or commercially valuable species, and not for inferring anything about people who appear in or are associated with the images.

#### Factors

###### Groups

The model's inputs are photographs of organisms, not of people, so age, gender, skin type and socioeconomic status are not attributes of any input and no demographic evaluation applies to the organisms. Two human-related factors nonetheless exist. Photographs from citizen-science platforms can contain bystanders, hands, faces, vehicles, licence plates and dwellings; the pipeline does not detect or redact them, and the sample set includes a bird held in a hand. And the pretraining corpus reflects where people photograph organisms: the upstream card states that TreeOfLife-200M is long-tailed across taxa, so recognition is strongest for well-photographed taxa in well-photographed regions and weakest for rare, cryptic, deep-sea, microscopic and tropical taxa, for immature and non-breeding forms, and for specimens rather than living organisms. The relevant "groups" are therefore taxonomic and geographic: the operator must evaluate on their own taxa and habitats, because an aggregate accuracy on common North American birds — which is exactly what the tutorial measures — says nothing about a poorly represented clade.

###### Instrumentation

The instrument is a camera in the field, and its factors dominate: focal length and distance (a small bird in a wide frame survives the 224×224 centre crop poorly or not at all), lighting and weather, motion blur, occlusion by vegetation, background habitat, whether the subject is a live organism, a museum specimen, a camera-trap frame at night, or a hand-held individual, and the JPEG compression applied by the platform that hosted the photo. The pipeline applies one fixed preprocessing — resize the shorter side to 224 px, centre-crop, normalise with the CLIP mean and standard deviation from the pinned config — and no augmentation, detection or cropping to the subject. The labels are the second instrument: whether a label comes from a research-grade community identification (as the sample does), a specialist, or a database with its own error rate passes directly into both the zero-shot prompts and the fine-tuned head, and a misidentified training photo is learned as truth. At inference the pipeline passes the caller's image bytes verbatim and detects only what decoding detects: format, size and undecodable data.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `torchvision==0.29.0`, `open_clip_torch==3.3.0` (with its runtime dependencies `timm==1.0.29`, `ftfy==6.3.1`, `regex==2026.9.10`), `huggingface-hub==1.32.0`, `safetensors==0.8.0`, `pillow==12.3.0`, `numpy==2.5.3` (`pyproject.toml`); the loader maps to CPU and moves the model to `device`, which defaults to `cuda:0` when CUDA is visible. Only float32 is exercised. Verified locally in a dedicated virtual environment on `torch 2.14.0+cpu`; the recorded CPU run is under "Runtime" (snapshot verification 1.0 s, load 6.6 s, 8 images embedded in 1.7 s, head-only adaptation with five validation evaluations 19.2 s). The 1.71 GB weight download dominates a fresh runtime. Memory: the base model is 1.7 GB in float32 and `adapt` copies the 1.2 GB image tower, so about 3.5 GB is needed on the default path. Data environment: the model assumes colour photographs of organisms resembling TreeOfLife-200M — museum, citizen-science and camera-trap imagery. Its behaviour degrades, without any error, on drawings, spectrograms, micrographs at unusual scales, multispectral data and images whose subject is not an organism. For the classifier the load-bearing assumption is that evaluation images are independent of training images; if they share an individual, a photographer or a site, the reported metrics measure memorisation of that source, and the pipeline cannot detect this for the operator.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.classification_metrics` names them: `accuracy`, `macro_f1` (unweighted mean of per-class F1 over classes present in the split), `per_class` precision/recall/F1 with `support` and `predicted` counts, and `auroc` (binary: positive class is the last entry of the class list; multiclass: macro one-vs-rest, from the Mann-Whitney rank statistic with average ranks for ties). Species datasets are almost always imbalanced — common species dominate — so macro-F1 and the per-class rows are the honest headline, and AUROC measures ranking quality independently of the argmax. Three baselines are reported with the same fields. `zero_shot_evaluate` is the **model's own prior** — what it scores with no training — and is the baseline every adapted number must be read against; the tutorial also runs it with common names in place of scientific ones. `majority_baseline` predicts the most frequent training class. `color_baseline` reduces each image to six numbers (mean and standard deviation of R, G, B on a 32×32 thumbnail), fits one centroid per class on the training split only, and assigns each test image to the nearest one; colour is the confounder worth ruling out in a species task, and the sample's four species were chosen a priori to make it weak. The embedding stage reports **no** performance measure. The executed CPU run under "Runtime" is sample-sanity evidence on 48 field photographs, not a benchmark; **no upstream benchmark number — NABirds, Rare Species, Meta-Album or any other — is reproduced or claimed in this repository.**

###### Decision thresholds

The default decision rule for both `zero_shot` and `classify` is an `argmax` over a softmax — an implicit threshold, and the only one the pipeline applies. No tuned operating point ships: the full per-class score dictionary is returned alongside the argmax label so a deployment can apply its own rule, and calibrating that rule is the operator's job. Two properties of the scores matter for any rule. Zero-shot scores are a softmax over **the supplied label set only**: on the sample, a blank grey image was labelled a white-throated sparrow at 0.5276 and a uniform-noise image at 0.8531, because a closed set always answers; an operator who needs "none of these" must add distractor labels or threshold on the raw cosine, neither of which the pipeline does for them. And the adapted head's scores are softmax outputs of 3,076 parameters trained on 28 images. In a triage context the asymmetry is usually that a missed record of a species of concern costs more than a false alert, which argues for a permissive threshold plus expert review of the borderline band. The limits that *were* fixed during development are input-contract limits, not decision thresholds: 32 images per call, 64 labels, the pixel-size ceilings, and the dataset minimums and maximums.

###### Approaches to uncertainty and variability

Reported metrics come from a **single seeded holdout**: `split_dataset` stratifies by class with an explicit seed (default 42) into train/validation/test, and `evaluate` scores one split once. No cross-validation, bootstrap or repeated-run averaging is performed, and no dispersion is reported — with a 12-image tutorial test split, any interval would be dominated by the split. A caller who needs one repeats the workflow over seeds, or supplies enough labelled data for k-fold with observation- or site-aware folds, and owns that design. Sources of run-to-run variability: the split, training shuffling and any random head initialisation are seeded through `random.seed` and `torch.manual_seed`/`torch.cuda.manual_seed_all`; non-deterministic GPU kernel selection and float accumulation order are **not** seed-controlled. Inference is deterministic in the sense that matters: the same batch embedded twice returns identical vectors (asserted in the tutorial), while embedding one image alone versus inside a batch of eight differed by at most 1.0×10⁻⁷ on CPU — float accumulation order, not stochastic inference — so a caller who needs bit-identical embeddings must fix the batch composition. The per-class scores are **not calibrated probabilities**, and a caller who needs calibrated confidence must fit a calibrator on held-out labelled data. Embeddings carry no uncertainty estimate of any kind.

#### Ethical considerations and biases

###### Data

Upstream discloses the pretraining data as TreeOfLife-200M (revision `a8f38b4` of `imageomics/TreeOfLife-200M`, assembled from GBIF, BIOSCAN-5M, EOL and FathomNet) plus a 26-million-sample LAION-2B subset for replay, and the upstream card points to the dataset card's considerations section for the long-tailed distribution and provenance discussion; the LAION-2B subset is web-scraped image-text data whose per-image licensing and content the upstream authors do not enumerate. Whether any specific pretraining image carries a licence encumbrance, depicts an identifiable person, or reveals a sensitive location is not established either way by the upstream authors — unknown, not ruled out. The upstream card is explicit that TreeOfLife-200M carries no geo-tags, to minimise poaching vulnerabilities. This repository distributes code, tests, documentation and **48 photographs**: research-grade iNaturalist observations whose *photo* licence code was checked to be CC0 1.0 when the set was built, centre-cropped to 224×224, with the observation URL, photo id and observer login recorded per image and **no location collected** (`src/bioclip2_biodiversity_pipeline/sample_data.py`; the build script is described in `docs/WEIGHTS.md`). The photographs are unfiltered beyond licence and quality grade, and were not reviewed for bystanders; one shows a bird held in a hand. It does **not** vendor the weights in Git. The operator owns the audit of whatever they submit: camera-trap frames capture people, citizen-science photos carry EXIF location by default, and a set of photographs of a protected species at a known site is exactly the record the upstream authors warn about. Inference is local and transmits nothing, which bounds exposure but discharges none of those obligations — and the hosted-runtime warning in the tutorial exists because pasting geotagged field photos into a cloud notebook is the realistic failure mode.

###### Human Life

This pipeline is not intended for decisions in health, safety, criminal justice, employment, credit, or housing, and it has not been validated or certified for any of them by anyone. No experimental validation, no regulatory clearance, no external review board and no testing with any specific group has taken place; the only evidence in this repository is the offline unit suite (42 tests), one local CPU run and one fresh-container Tesla T4 run on 48 photographs of four common birds. Use in a sensitive domain is nevertheless foreseeable — species identification feeds wildlife-crime enforcement, biosecurity and invasive-species response, disease-vector surveillance and conservation triage — and would be admissible only with task-specific validation on the deployment's own taxa, habitats and cameras, a specialist confirming every consequential identification, and whatever legal process the domain requires. A predicted species from this pipeline is a hypothesis for an expert, never a determination.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of all 3 manifest entries before any load and raises on the first mismatch (tests flip a digit, change the revision and delete a file and assert each raises), and refuses a manifest that omits the config or the weights file. `stage_missing_files()` fetches only manifest-listed files absent on disk, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. `.gitattributes` carries `weights/** -text`.
2. **No remote code and no registry lookup:** the model is built from the pinned `open_clip_config.json`, whose architecture fields are asserted against the package constants before any model library is imported, and the weights are loaded with `strict=True` — 0 missing, 0 unexpected keys. Nothing from the Hub is executed.
3. **Artifact integrity:** the adapter is safetensors, not a pickle, and `load_artifact` checks the artifact format, the recorded base model id and revision, the class list, and the size and SHA-256 of every listed file **before** deserialising, then refuses any tensor name the classifier architecture does not have.
4. **Input integrity:** `embed_images`, `zero_shot`, `classify` and `validate_inputs` route through one checker, so their acceptance criteria cannot diverge; it decodes every image, rejects undecodable data, unsupported formats, undersized and oversized images, too many images, and id lists that are the wrong length or not unique, and records each image's digest. `validate_dataset` additionally rejects missing fields, duplicate ids, duplicate image bytes, fewer than 2 or more than 50 classes, and any class with fewer than 3 records. Label sets are checked for size, uniqueness and prompt length.
5. **Import boundary:** verification and validation run before `torch`, `open_clip` or `safetensors` are imported (fleet RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library.
6. **Statistical mitigations:** `split_dataset` stratifies by class; the head is initialised from the zero-shot classifier so epoch 0 is a known quantity; validation metrics are monitoring only and the final epoch is kept rather than the best; the frozen tower is the default so 28 images cannot rewrite 300 million parameters; three baselines are computed on the same split so a number always has a floor and a ceiling.
7. **Score honesty:** the zero-shot decision rule string says the scores are relative to the supplied label set, and the tutorial demonstrates a confident label on a blank image and on noise before any adapted number is shown.
8. **Sample-data hygiene:** per-image CC0 licence codes were verified at build time, provenance is recorded, and locations were deliberately not collected.

Not implemented, and therefore not claimed: no open-set rejection, no detection or subject cropping, no observation- or site-aware splitting, no calibration, no bystander or EXIF scrubbing of user images, and no applicability-domain estimate.

###### Risks and harms

1. **Closed-set overconfidence:** a zero-shot call always returns one of the supplied labels with a softmax score, and the sample showed 0.85 on pure noise. An operator who reads the score as "probability this is a bird" will file confident nonsense.
2. **Long-tail failure without signal:** rare, cryptic, immature, non-breeding, tropical and specimen imagery are under-represented upstream; the model's answer on them is as confident as on a common bird, and nothing in the output says so.
3. **Source leakage inflating every metric:** photographs of one individual, one photographer or one site across a random split turn memorisation into apparent generalisation. Likelihood is high for any dataset assembled from a single project, and neither the model nor this repository can detect it.
4. **Centre-crop losing the subject:** a small organism in a wide frame can be cropped away entirely; the pipeline then classifies the habitat.
5. **Location disclosure:** the harm the upstream authors name explicitly. Field photographs carry EXIF location by default; a labelled dataset of a protected species uploaded to a hosted runtime, or an adapter artifact whose metadata names a site, is the realistic leak.
6. **Dual use:** an identifier for threatened species serves monitoring and poaching alike. The upstream card argues the primary risk is location data rather than classification capability; this repository shares that assessment and collected no locations.
7. **Bystanders and people:** field and camera-trap imagery captures people; the pipeline does not detect, redact or refuse them, and embeddings of such images are representations of the people in them.
8. **Uncalibrated scores read as probabilities:** a head trained on a few dozen images yields a ranking, not a calibrated confidence; a triage pipeline that treats it as one will mis-state its own hit rate.

###### Use cases

The model must not be used to locate, track, target or facilitate the taking of protected, threatened, endangered or commercially exploited species, nor to identify specimens in illegal trade for the purpose of that trade; it must not be used to identify, profile or infer anything about people who appear in or are associated with the images, including their location, habits or property; it must not be used to produce species determinations presented as authoritative for regulatory, legal, biosecurity, medical or veterinary purposes without expert confirmation; it must not be used to generate model-predicted identifications deposited into biodiversity databases (GBIF, iNaturalist, museum records) without marking them as predictions, which would pollute the corpora future models train on; and it must not be used in any way that breaches the MIT terms of the upstream weights or the DIMER deployment terms. The sample photographs are CC0 and carry no location, but a BYOD set of field photographs usually does, and the iNaturalist community norm of obscuring locations of sensitive taxa applies to anything derived from them. These prohibitions hold even where the model would produce an accurate answer.

## Input/output contract

- `BioClip2Pipeline.from_pretrained(device=None, weights_dir=None, allow_download=False)`: stages and verifies the snapshot, asserts the pinned config's architecture fields against the package constants, builds `open_clip.model.CLIP` from that config, loads the safetensors strictly, builds the image transform from `preprocess_cfg` and the bundled BPE tokenizer; `device` defaults to `cuda:0` when visible, else `cpu`.
- `embed_images(images, *, names=None) -> dict` with `ids`, `embeddings` (one L2-normalised 768-float vector per image), `dimension`, `pooling`, `unit`, `images` (id, width, height, sha256), `n_images`, `model_id`, `model_revision`.
- `embed_texts(texts) -> dict` with `texts`, `embeddings`, `dimension`, `n_texts`, `model_id`, `model_revision`.
- `zero_shot(images, labels, *, names=None, template="a photo of {}.") -> dict` with `predictions` (each `{id, sha256, label, score, scores}`), `classes`, `prompts`, `template`, `logit_scale`, `decision_rule`, `n_images`, `model_id`, `model_revision`; `labels` is a list of names or a `{label: name}` mapping.
- `zero_shot_evaluate(records, class_prompts, *, template=...) -> dict`: the classification metrics of the zero-shot classifier on a labelled dataset, labelled `baseline: "zero-shot (text classifier, no training)"`.
- `adapt(train_records, val_records=None, *, classes=None, class_prompts=None, template=..., epochs=4, learning_rate=1e-4, batch_size=8, trainable_blocks=0, weight_decay=0.01, seed=42) -> dict`: bounded AdamW fine-tuning; returns the method description, `head_initialisation` (`"zero-shot text classifier"` or `"random"`), class list, hyperparameters, trainable/total parameter counts, trainable parameter names, split sizes, the selection rule and the per-epoch history, whose epoch 0 entry is the untrained head on the validation split.
- `evaluate(records) -> dict`: `n`, `accuracy`, `macro_f1`, `per_class`, `classes`, `decision_rule`, `auroc`, `auroc_definition`.
- `classify(images, *, names=None) -> dict` with `predictions` (each `{id, sha256, label, score, scores}`), `classes`, `decision_rule`, `n_images`, `model_id`, `model_revision`, `adaptation`.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` + `manifest.json` (format, base model id/revision/licence, `requires_remote_code: false`, class order, tensor names, empty `serving_state_tensors`, file size and SHA-256, adaptation record); `from_artifact(...)` / `load_artifact(...)` verify all of that before deserialising.
- `validate_inputs(images, *, names=None)` and `validate_dataset(records, *, classes=None, min_records=8, min_per_class=3)` return the input and dataset manifests; both raise exactly what the execution path would raise. `decode_image(image)` and `image_digest(image)` are the shared primitives.
- Constants: `EMBED_DIM = 768`, `IMAGE_SIZE = 224`, `VISION_LAYERS = 24`, `CONTEXT_LENGTH = 77`, `VOCAB_SIZE = 49408`, `MIN_IMAGE_SIDE = 32`, `MAX_IMAGE_SIDE = 8192`, `MAX_IMAGES_PER_CALL = 32`, `MAX_LABELS = 64`, `MAX_PROMPT_CHARS = 200`, `ACCEPTED_FORMATS = ("JPEG", "PNG", "WEBP")`, `DEFAULT_PROMPT_TEMPLATE = "a photo of {}."`, `ARTIFACT_FORMAT = "org.valcorza.bioclip2-biodiversity.adapter.v1"`.

## DIMER deployment notes

| Field | Status |
|---|---|
| **DIMER status** | **Planned** — no gate open on licence or remote code; GPU budget and the fine-tuning recipe are the operational questions |
| Licence | MIT — use, modification, redistribution and commercial use permitted with the licence and copyright notice preserved |
| Weights | Would be redistributed unmodified; this repository redistributes none and stages them from the pinned revision |
| Remote code | **Not required** — plain safetensors state dict into open_clip's own module; `trust_remote_code` is never passed |
| Runtime | `open_clip_torch==3.3.0` (+ `timm`, `ftfy`, `regex`), not `transformers`; a DIMER runtime for this model is an open_clip runtime |
| Upload format | `open_clip_model.safetensors` (1,710,517,724 bytes) + `open_clip_config.json`; the `.bin` twin must not be uploaded |
| Compute | CPU serving is viable for embeddings and zero-shot (≈0.3 s per image on the recorded CPU); head-only adaptation runs on cached features; unfreezing the tower is where GPU budget and the domain-fine-tuning policy DIMER calls for become material |

This profile is classed GPU-heavy, with a DIMER domain-fine-tuning recipe, a GPU budget and a replay/domain-shift policy as prerequisites. This repository's evidence bears on that: with a few dozen labelled images the right recipe is head-only on cached features, which is CPU-cheap and did not degrade a saturated zero-shot classifier, while unfreezing one tower block did. A profile that offers tower fine-tuning should require far more labelled data per class than the tutorial uses and should evaluate on an observation- or site-aware split.
